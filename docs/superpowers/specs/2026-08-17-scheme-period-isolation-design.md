# 方案期号同步隔离与跨期保护设计

## 目标

避免第三方期号接口缓慢或不可用时导致方案工作器漏期；任何单个彩种、方案或网络请求异常都不得阻塞其他彩种的下注、结算或方案执行。

## 已确认的问题

当前方案工作器在每个 tick 开始时同步等待 `prefetchPeriodSync`。该调用会等待所有运行彩种的 `EnsureFreshIfStale` 返回。与此同时，后台期号同步器每 3 秒运行一次且单轮最多按顺序刷新 4 个彩种。第三方 `/api/web_bets/lott/periods` 出现连接或 TLS 超时时，短周期彩种会错过下注窗口。

严格下单期号仍必须来自第三方 periods 缓存。WebSocket 仅用于开奖与诊断，不能作为下单期号的替代来源。

## 方案

### 1. 期号刷新隔离

引入按彩种管理的刷新调度器：

- 每个彩种同一时刻最多一个在途刷新（single-flight）。
- 方案工作器仅提交非阻塞刷新请求，然后继续处理全部方案实例；它绝不等待任何 HTTP 请求。
- 后台调度器以有界并发执行刷新，短周期彩种优先，普通彩种保持较低优先级。
- 每次刷新均使用独立的短超时 context；超时后释放并发槽位，不累积 goroutine 或连接等待。
- 同一彩种失败后使用有限退避，仅抑制该彩种的重复刷新，不影响其它彩种。

### 2. 下单与窗口安全

- 下单链路只读取最近一次已验证的 periods 缓存。
- 缓存无可投注期号时，本次仅跳过该实例；后台刷新继续进行，不在下单路径同步拉取。
- 不使用 WebSocket 推导或替代下单期号。
- 第三方返回的实际接受期号若与目标期号不同，保存实际期号和诊断详情，立即把该方案实例自动暂停为 `bet_failed`；不补投、不重投，也不将请求改投下一期。

### 3. 全局资源边界

- 刷新调度器配置固定的最大并发数，防止运行彩种增多时请求风暴。
- 下单并发继续使用既有独立的 `placeSem` 上限，不与期号刷新共享队列。
- 结算、维护恢复和方案 tick 不等待刷新调度器完成。
- 所有异步任务接受服务根 context，在服务关闭时可取消。

### 4. 开发者诊断

按彩种保存并在管理员方案运行诊断中暴露：最近刷新成功时间、最近尝试时间、最近耗时、连续失败数、下一次允许刷新时间和最近错误摘要。仅供开发者排查，不展示给普通用户。

## 验收标准

1. 一个彩种的刷新阻塞超过其超时，不延迟另一个彩种的方案处理。
2. 同一彩种的并发刷新数始终不超过 1；总刷新并发不超过配置上限。
3. 当 periods 缓存有效时，方案工作器不会进行同步网络等待。
4. 第三方确认接受到不同期号时，实例自动暂停且不会发生自动补投。
5. 原有严格期号校验、下单去重、下单并发限制与结算流程保持不变。

## 测试策略

- 使用可控阻塞的 periods 拉取器验证跨彩种隔离与超时释放。
- 验证 single-flight、失败退避与短周期优先顺序。
- 验证缓存缺失只跳过当前实例，不阻塞其它实例。
- 验证跨期返回会持久化实际期号并暂停实例。
