# 短周期正式方案结算与策略推进修复设计

## 背景

方案 `def-1-1786600039310`（实例 `inst-1-1786600039439`）运行于波场 3 秒彩，现场存在三个相互关联的问题：

1. 正式下注前同步调用第三方余额接口，再调用第三方下注接口，单次出站链路耗时接近短周期封盘窗口，造成漏期。
2. 目录玩法 `fast_ssc_std/g017/390` 在解析后同时包含 `CatalogSubID=390` 与语义化 `SubPlayID=daxiao`；发布规则冻结错误地只使用 `SubPlayID`，导致正式注单缺少规则快照。
3. 第三方派彩批量查询失败时被静默忽略，开发诊断无法区分网络超时、第三方尚未结算与本地处理失败。

## 目标

- 方案开启前只查询一次第三方可用余额。
- 方案运行后不再于每笔下注前查询余额，直接调用第三方下注接口。
- 第三方返回余额不足时，转换为平台统一的余额不足错误并按既有流程停止方案。
- 新正式注单冻结与目录玩法一致的已发布规则，在开奖入库后及时推进策略轮次。
- 第三方仍是正式注单状态、盈亏和派彩金额的唯一资金权威。
- 派彩查询失败必须留下可供开发者定位的日志和运行诊断。
- 任何情况下都不得为了补期而向已封盘期或下一期强行发送下注。

## 非目标

- 不修改第三方派彩金额、输赢状态或钱包流水的权威来源。
- 不使用当前规则追溯回算历史上没有冻结规则快照的正式注单。
- 不承诺第三方网络异常时每个 3 秒周期都能成功下注。
- 不改变普通方案的启动前最低投注金额和余额预检规则。
- 不增加用户端诊断展示；新增诊断仅供管理员和开发者使用。

## 设计

### 1. 余额查询移出运行期下注临界区

保留 `schemes.Service.ensureUsableBalanceForStart` 现有启动前预检。方案成功开启后，`accountsvc.Service.placeRealBetWithRow` 不再调用 `UserInfo` 检查余额，直接解析账号授权、构造注单并调用 `PlaceLottBet`。

第三方下注返回错误时，新增严格的余额不足识别：依据第三方错误消息中的明确语义（例如“余额不足”或 `insufficient balance`），不能只依据通用错误码 `40000`，因为该错误码还可能表示金额参数不一致。识别成功后返回 `guajibet.ErrInsufficient`，继续复用 worker 现有的余额不足暂停流程。

派奖完成后的余额刷新不在下注临界区内，继续保留，用于钱包镜像和余额展示。

### 2. 目录规则定位与冻结

发布规则解析按以下候选顺序查找：

1. `playRule.CatalogSubID`
2. `playRule.SubPlayID`

候选值去空白、去重；每个候选都使用相同的 `PlayTemplate`、`PlayTypeID` 和 `LotteryCode` 调用规则注册表。目录 ID 命中后立即返回，不再被语义化运行模式覆盖。

对于本方案，定位从错误的 `fast_ssc_std/g017/daxiao` 修正为 `fast_ssc_std/g017/390`。下注占位成功后，在第三方请求之前冻结规则版本、内容哈希和评估规格。开奖 WS 入库后，现有 `StrategyProcessor` 使用冻结快照推进轮次；第三方派彩到达后只补资金状态和执行策略对账，不重复推进轮次。

历史上 `rule_snapshot IS NULL` 的正式注单继续等待第三方派彩，不自动写入当前规则，以免规则版本穿越。

### 3. 派彩同步诊断

`PayoutSyncWorker.syncAccountPending` 调用第三方批量注单列表失败时，不再返回 `nil`。错误返回到账号批次边界，由现有 worker 统一输出包含账号 ID、待处理数量和错误详情的警告日志；下一轮仍按原 10 秒周期重试，数据库 pending 记录不丢失。

增加账号级内存诊断快照，至少包含：

- 最近尝试时间
- 最近成功时间
- 最近错误及错误时间
- 本轮待处理注单数
- 第三方列表返回数量
- 本轮成功结算数量
- 第三方仍未结算数量

管理员方案运行诊断接口根据实例使用的挂机账号附带该快照。该诊断只读、不触发第三方请求，也不影响派彩 worker 的执行。

### 4. 漏期与跨期边界

移除每笔下注前的 `UserInfo` 后，正式下注临界区只保留必要的期号校验、封盘安全窗口检查和一次 `PlaceLottBet`。已有彩种级 periods/WS 快照继续共享，不增加每方案轮询。

若等待并发槽或第三方请求时已经失去安全窗口，该期必须跳过。第三方返回接单期与目标期不一致时，继续记录实际接单期并暂停方案，禁止将其伪装成目标期。

## 错误处理

- 启动前余额不足：保持现有“无法开启”响应。
- 运行中第三方明确返回余额不足：转换为余额不足状态并停止方案。
- 运行中第三方传输错误：保持注单占位并按既有安全策略重试或等待下一轮，禁止不确定性重复下注。
- 派彩列表查询失败：保留 pending，写入诊断并在下一轮重试。
- 第三方返回未结算：保留 pending，诊断计入“第三方未结算”。
- 本地规则不存在：不阻断兼容玩法下注，但规则诊断保持 `missing_rule_snapshot`；已发布目录规则必须通过测试确保能够命中。

## 测试策略

### 规则快照

- 使用实际配置 `fast_ssc_std/g017/390 + betMode=daxiao`，先证明旧定位只查到 `daxiao` 而失败。
- 修复后断言优先命中 `CatalogSubID=390`，并冻结版本与哈希。
- 断言没有目录 ID 的兼容玩法仍可回退语义化 `SubPlayID`。

### 余额与下注

- 断言运行期正式下注不会调用 `UserInfo`，只调用一次 `PlaceLottBet`。
- 断言明确的第三方余额不足消息映射为 `guajibet.ErrInsufficient`。
- 断言相同通用错误码但非余额语义不会误判为余额不足。
- 保留并运行启动前余额预检现有测试。

### 派彩诊断

- 断言批量列表查询错误会返回并记录诊断，而不是静默成功。
- 断言第三方返回未结算与请求错误分别计数。
- 断言后续成功会更新最近成功时间并清理当前错误状态。
- 断言管理员运行诊断接口只读取内存快照，不触发第三方调用。

### 回归验证

- 运行 `go test ./internal/schemes ./internal/guaji ./internal/guaji/accountsvc ./internal/handler -count=1`。
- 运行 `go test ./... -count=1`。
- 部署后观察新注单满足 `period_no = third_party_period`、`rule_snapshot IS NOT NULL`，并核对开奖后的策略评估状态。

## 发布与回滚

本修复不新增数据库迁移。发布后重启后端即可加载代码和已发布规则。旧无快照注单继续由现有派彩 worker 处理。

若运行中余额不足识别出现误判，可回滚代码恢复下注前余额查询；数据库记录格式无变化。规则定位与派彩诊断均为向后兼容修改，可独立保留。
