# WebSocket 策略推进与第三方结算解耦设计

## 目标

对真实盘方案，在上一期 `N` 开奖后 3 秒内完成本地策略判定，并在不跨期的前提下为 `N+1` 期计算下注内容、倍数和轮次。第三方仅作为实际扣款、派奖金额和最终账务的权威来源，不再阻塞策略推进。

## 边界

- 本地策略结果：使用已写入 `lottery_draws` 的 WebSocket 开奖号码，按与下注时一致的玩法、投注内容和经验证的规则模型判定命中/未中；只推进方案状态，不直接记资金。
- 最终资金结果：继续以第三方 `web_bets` 的 `settled`、`net_amount` 和 `payout_amount` 为准，异步更新订单、投注记录、账本和余额。
- 第三方最终结果与本地策略结果不一致时，停止该实例并留下开发诊断；不得静默以任一方覆盖另一方。
- 不承诺第三方在 3 秒内完成结算；承诺本平台收到 WebSocket 开奖后不因第三方结算轮询而延迟策略推进。

## 权威判定规则

- `C:\Users\Administrator\Desktop\v5赔率核对表.xlsx` 是规则整理的原始依据：`A` 为规则 ID、`E` 为规则全名、`F` 为中奖条件、`G` 为投注与开奖号码示例，`H-L` 为号码范围、全注数、可中注数和赔率，`P` 为单挑注数。
- Excel 仅用于一次性导入和人工核对；运行时、测试和后台编辑均以数据库为唯一规则源，不再读取 Excel。
- 目录仍只使用现有 `play_templates → play_types → sub_plays`。新增一张一对一的 `play_rule_specs` 规则扩展表，以 `(template_code, type_id, sub_id)` 唯一关联玩法目录；不新建平行的彩种或玩法目录。
- `play_rule_specs` 的一行只保存当前已发布规则：`rule_version`、结构化 `evaluation_spec`、`sample_cases`、来源元数据及更新时间。`evaluation_spec` 覆盖中奖判定、号码范围、注数/赔率/单挑限制和必要的玩法参数；`sample_cases` 保存可自动执行的示例与边界用例；来源元数据保留 Excel 行 ID 和导入批次，仅供审计，不参与运行。
- 规则采用“模板默认 + 彩种覆盖”的作用域：默认规则按目录自然键匹配，确有差异时以 `lottery_code` 覆盖，并设定生效区间。生肖、波色等依赖年份或开奖属性的数据必须声明 `attribute_calendar_version`，并随注单快照冻结。
- 规则修订记录写入仅供后台审计、验证和回滚的追加表 `play_rule_spec_revisions`，并具有 `draft → verified → published → disabled` 状态；它不参与目录查询、规则缓存和开奖热路径。运行态始终只读取 `play_rule_specs` 的当前发布版本，编辑草稿不会改变已有发布规则。
- 一次性导入按“目录自然键 + 第三方 `rule_id` + 规则全名”生成待确认修订；同名或无法唯一匹配的行不得自动发布，必须在后台确认后才可提升为对应 `play_rule_specs`。
- 不以外键直接绑定 `sub_plays.id`：当前第三方目录同步会重建子玩法行。同步后按上述自然键做完整性校验，失去目录对应项的规则标记为不可用而非被删除，避免同步覆盖或丢失本地规则。
- 规则发布在一个事务中把已验证修订提升为当前规则、追加审计记录并递增 `rule_version`。第三方目录同步只更新目录和 `outbound_play_code`，不得覆盖 `play_rule_specs`。
- 方案创建和第三方接单成功时，冻结 `rule_version` 与最小可执行规则快照到对应的方案状态/注单记录；历史注单永远按下注时冻结的版本判定，无需查询历史规则表。
- 当前模拟通道的判定实现不是权威来源。真实方案和模拟通道最终都调用同一个“权威玩法判定器”，但只有在该玩法已完成样例验证后才允许真实方案使用其结果推进倍数和轮次。
- 每个映射玩法至少具备表中示例、边界号码、复式/组选等形态样例，并以第三方已结算历史注单进行对账。规则未映射、样例未通过或对账不一致时，仅暂停对应方案实例的本地策略推进并记录 `strategy_rule_unverified` 诊断；不得影响其他实例，也不得按模拟通道结果猜测推进。

## 判定器与规则发布

- 数据库是业务规则、参数和版本的唯一来源，不在数据库中保存或执行任意 Go/SQL 脚本。每条规则指定受控的 `evaluator_key`；代码只提供固定、可单测的通用判定器，例如直选、组选、和值、属性盘、生肖/波色和对碰。
- `evaluation_spec` 使用按 `evaluator_key` 定义的固定结构，至少声明号码宇宙、位置、判定模式、组选/直选约束、注数上限、单挑限制、赔率参数及判定器版本。发布前必须通过结构校验和 `sample_cases` 自动测试，自由文本描述不得参与运行判定。
- 规则修订状态固定为 `draft → verified → published → disabled`。只有已提升到 `play_rule_specs` 的 `published` 修订可用于真实方案；每次发布记录操作者、时间、变更原因、旧版本和新版本，并支持将当前规则回滚到已验证版本。
- 初始导入和后续规则变更都先以 `draft` 修订写库，与第三方已结算历史注单做影子对账；达到该玩法的样例与历史对账要求后转为 `verified`，再由管理员发布。影子对账不推进真实方案状态。
- 接单成功的注单快照至少包含 `evaluator_key`、判定器版本、`rule_version`、规范化投注内容及其哈希。策略推进只使用该不可变快照，避免规则发布后重算历史期造成倍数或轮次漂移。

## 查询与缓存

- 规则表不是开奖热路径。服务启动、规则发布或缓存失效时，以一次带索引的目录 JOIN 加载全部已验证规则到进程内只读缓存，键为 `(play_template, type_id, sub_id, rule_version)`。
- WebSocket 开奖、策略判定和下单重试只读取冻结快照或内存缓存，不会对每个方案、每期或每笔注单执行规则 JOIN。
- 后台目录查询使用一次带唯一索引的 JOIN 返回玩法与当前规则；规则数据量远小于订单和开奖数据，不形成数据库瓶颈。
- 发布规则后向全部服务实例发送缓存失效事件；未收到事件的实例在短周期版本检查时重新加载。规则版本以数据库为准，缓存版本未知或刷新失败时仅拒绝相关玩法的本地策略推进，不得用疑似过期规则创建新注单，也不影响其他玩法和实例。

## 数据流

1. WebSocket 收到已开奖期 `N`，幂等写入 `lottery_draws` 并发布内部开奖事件。
2. 开奖事件不是只存在于内存：持久化的策略判定表以 `(instance_id, period_no)` 唯一，记录待处理、处理中、已完成或跳过。WebSocket 仅负责低延迟唤醒；服务启动和短周期恢复扫描从 `lottery_draws` 与已接单注单找回未完成记录，重复事件幂等。
3. 策略执行器按实例 ID 分片。每个实例在同一时刻仅处理一个开奖事件，不同用户和实例可并行处理。
4. 执行器定位该实例 `N` 期已经被第三方接收的注单，以冻结的实际投注内容、本期倍数、下注时冻结的规则版本和本地开奖结果计算策略命中结果。
5. 在一个数据库事务中写入策略判定、推进 `round_index`、`pick_index`、`current_pick`、`last_direction`，并以 `(instance_id, period_no)` 唯一键和实例行锁保证同一期最多推进一次。
6. 方案 worker 只在已看到 `N` 的策略推进完成后准备 `N+1`；出站前仍要求 periods 缓存的当前可投期严格等于目标 `N+1`，且满足封盘安全余量。
7. 第三方结算 worker 改为按 Guaji 账号批量拉取注单列表。一次响应匹配该账号多个本地 pending 注单，异步写入最终盈亏和账务，不阻塞步骤 1 至 6。

## 性能与时限

- WebSocket 入库和事件入队目标小于 300ms。
- 单实例策略判定与状态事务目标小于 100ms。
- 开奖事件触发后立即调度下期，不依赖 10 秒定时轮询；正常情况下在 3 秒周期内完成下一期准备。
- 第三方结算按账号单飞：同一账号同一时刻最多一个列表请求；不同账号受全局有界并发控制。
- 对尚未 `settled` 的注单采用短退避（0.5s、1s、2s、3s）后降级为低频轮询；不得对每笔订单先请求已知会 404 的详情接口。
- 策略队列按分片设置长度、等待时间和积压指标。队列满时只合并重复唤醒，待处理事实仍保留在数据库；若该实例已无法满足下一期封盘安全余量，则将该期标记为跳过并保留开发诊断，绝不排队迟到下注或跨期下注。其他分片继续运行。

## 跨期与一致性

- 下注目标期只能为已完成本地策略判定的开奖期之后的下一开放期；不允许将请求发到第三方已切换的期号。
- 下单占位、第三方接单期号、策略判定期号和最终结算期号均保留独立字段，禁止用 `last_settled_issue` 混合表达。
- 实例状态使用乐观版本或行锁串行化；重复 WebSocket、重启重放和并发 worker 均不得重复推进倍数/轮次或重复下单。
- 本地判定与第三方对账比较期号、第三方已接收期号、规范化投注内容哈希、命中/未中和中奖注数；净盈亏、返水、赔率差异与金额截断只作为诊断字段，不作为不一致的单独判据。第三方延迟 `settled` 不阻塞本地策略推进。

## 灰度与切换

- 本地策略按 `(lottery_code, evaluator_key)` 功能开关灰度启用，默认关闭；未启用或规则未验证的玩法维持现有结算链路。
- 开关只对启用后新被第三方接收的注单生效。已接单但尚未完成结算的旧注单继续按其原链路处理，不得在同一期中途切换判定来源。
- 灰度期间持续记录本地与第三方的对账结果；发现不一致只关闭对应彩种/玩法开关并暂停相关实例，其他彩种、玩法和用户不受影响。

## 可观测性

每笔真实注单记录：开奖到达时间、本地策略判定时间、首次结算查询时间、第三方首次 `settled` 时间、最终账务落库时间、查询错误和重试次数。管理员诊断接口按实例展示这些时间线与当前阻塞原因。

本地判定与第三方最终结果不一致时，诊断必须同时保留：实例与期号、目录自然键和第三方 `rule_id`、`evaluator_key`、规则/判定器版本、冻结规则快照、规范化投注内容、开奖号码、本地命中结果、第三方状态和盈亏。诊断将不一致归类为规则、投注格式、期号、开奖结果或第三方结算异常；无论类别都只暂停该实例。

## 验收

- 3 秒彩：模拟第三方结算延迟 60 秒时，WebSocket 开奖后 3 秒内仍完成下一期策略计算；最终账务在第三方返回后正确落库。
- 权威判定器：逐个核对已映射玩法的表中示例、边界样例和第三方已结算历史注单；模拟通道与权威判定器对同一输入必须得到相同命中结果。
- 数据库规则源：Excel 导入后，运行、测试和后台规则查询均只读取 `play_rule_specs`；第三方目录同步后规则记录仍可按自然键关联且不会丢失。
- 热路径性能：多实例并发开奖时，策略判定不产生逐实例规则查询；规则缓存命中并使用冻结版本，规则发布后所有服务实例可见新版本。
- 发布治理：未通过结构、样例和历史影子对账的规则不能发布；规则回滚后新注单使用新发布版本，既有注单继续按冻结快照处理。
- 宕机恢复：停止服务后重新启动，未完成的开奖策略判定可由持久记录补齐；重复 WebSocket 或恢复扫描不会重复推进或重复下单。
- 灰度与过载：开关切换不改变已接单注单的判定来源；高并发积压时只跳过无法安全下单的实例/期号，绝不跨期，其他实例正常运行。
- 未验证玩法：不发生本地倍数/轮次推进，只暂停该实例并返回可定位的规则版本、映射和样例校验诊断。
- 多用户、多实例并行运行时，每个实例每期最多一笔，状态推进顺序正确，无全局阻塞。
- periods 在出站前变化时跳过目标期，不产生 `target=N accepted=N+1`。
- 本地策略与第三方最终结果不一致时，实例停止且诊断可定位双方结果与时间线。
