# 云端中心 NATS 实时同步设计

日期：2026-08-18
状态：已确认，待实施

## 1. 背景

当前用户端云端中心通过 WebSocket 接收 `client.scheme.instance` 提示，但该消息只要求前端刷新，前端仍会调用：

- `GET /api/v1/client/cloud/schemes/running?ids=...`
- 云端中心统计接口

页面还会在倒计时结束、等待开奖和固定定时器触发时继续刷新。单用户已经会产生密集请求；多用户、多方案和多 API 节点部署后，请求量会随在线用户数增长，并给 API 和 PostgreSQL 带来持续压力。

本设计将云端中心改成“REST 初始化与重连对账，WebSocket 增量同步”，并通过 NATS Core 支持 Worker 与 API/WebSocket 服务跨服务器部署。

## 2. 目标

1. WebSocket 正常在线期间，停止云端方案卡片和统计数据的后台 REST 轮询。
2. 方案状态变化后直接向对应会员推送完整可变字段快照。
3. 同一方案短时间内的多次变化合并发布，减少数据库查询和消息数量。
4. 支持多个 Worker、多个 API/WebSocket 节点和多个服务器。
5. NATS、单个用户或单个连接异常不能阻塞方案计算、下注和结算。
6. 通过断线 REST 对账和数据库补偿扫描保证最终一致性。
7. 严格隔离会员数据，禁止跨账号推送。

## 3. 非目标

1. NATS 不取代 PostgreSQL，数据库仍是方案状态的唯一事实来源。
2. 本期不使用 NATS JetStream 保存业务状态或替代投注记录。
3. 本期不改变云端中心的分页、搜索、卡片排序和方案运行规则。
4. 本期不把倒计时本身交给服务端逐秒推送；前端仍根据封盘时间本地递减。

## 4. 方案选择

采用 **NATS Core + WebSocket 快照推送 + REST 强制对账 + 数据库补偿扫描**。

NATS Core 适合低延迟主题分发和集群节点间实时通知，但使用至多一次投递语义。因此它只承载可重复生成的状态快照，不承载不可重放的唯一业务事实。NATS 官方说明见：

- <https://docs.nats.io/concepts/what-is-nats>
- <https://docs.nats.io/nats-concepts/core-nats/queue>

消息总线抽象为内部接口，后续确有持久化、消费确认或重放需求时，可以在不改变上层业务代码的前提下迁移到 JetStream。

## 5. 总体架构

```text
Worker / 用户操作接口
        |
        | 标记 memberId + instanceId 已变化
        v
节点内 200ms 合并器（latest wins）
        |
        | 批量查询当前卡片投影
        v
按会员分组发布 NATS Core
        |
        v
仅订阅本节点在线会员主题的 API 节点
        |
        v
浏览器 WebSocket
        |
        v
直接更新已加载卡片和统计数据
```

REST 只负责：

- 页面首次加载；
- 搜索和分页；
- WebSocket 建立或重新建立后的单次全量对账；
- 用户主动操作接口的直接响应。

## 6. 主题设计和订阅模型

方案消息使用会员范围主题：

```text
caipiao.client.<memberId>.scheme
```

统计消息使用：

```text
caipiao.client.<memberId>.cloud_stats
```

API 节点维护本节点在线连接的会员引用计数：

1. 某会员第一个浏览器连接建立时，订阅该会员的 NATS 主题。
2. 同一会员新增连接时只增加引用计数，不重复订阅。
3. 最后一个连接断开时取消订阅。
4. 每个 API 节点只接收本节点存在在线连接的会员消息，不订阅全量会员事件。

NATS 主题不能成为授权依据。API 节点仍必须根据已认证 WebSocket 连接绑定的会员 ID 转发消息。

## 7. 方案状态生产与合并

### 7.1 变化标记

Worker 和用户操作接口完成数据库事务后，只向本机合并器提交：

```text
memberId, instanceId, changeKind
```

生产路径不逐事件查询会员，也不直接操作某个本机 WebSocket Hub。

### 7.2 合并策略

- 以 `(memberId, instanceId)` 为键。
- 同一键在 200ms 内多次变化只保留一次脏标记。
- 到期后一次批量加载全部实例的当前卡片投影。
- 以数据库中最终状态生成快照，因此中间状态不需要逐条发送。
- 一次刷新按会员分组；同一会员的多个实例放进同一条 NATS 消息。

### 7.3 容量控制

- 合并器使用有界队列和有界待处理映射。
- 队列压力过高时保留“实例仍然为脏”的事实，不堆积每次中间变化。
- 失败实例进入待补偿集合，不阻塞其他实例。
- 数据库查询和 NATS 发布均使用超时及分批大小限制。
- 单个批次失败不会停止下一批处理。

## 8. 消息协议

新 WebSocket 事件建议命名为：

```text
client.scheme.instances.snapshot
```

方案快照消息：

```json
{
  "schemaVersion": 1,
  "generatedAt": "2026-08-18T12:00:00Z",
  "items": [
    {
      "instanceId": "inst-1-xxx",
      "updatedAt": "2026-08-18T12:00:00Z",
      "status": "running",
      "statusReason": "",
      "statusLabel": "运行中",
      "turnover": "12.34",
      "pnl": "1.25",
      "sessionPnl": "0.50",
      "lookbackPnl": "2.10",
      "runningSince": "2026-08-18T11:30:00Z",
      "countdownPeriod": "85430018",
      "countdownCloseAt": "2026-08-18T12:00:03Z",
      "countdownWindowSec": 3,
      "multiplier": 1,
      "simBet": false,
      "currency": "USDT"
    }
  ],
  "removedIds": []
}
```

协议规则：

1. `schemaVersion` 用于前后端兼容。
2. `updatedAt` 是实例级版本；前端拒绝比当前实例版本旧的快照。
3. 每个 `item` 是卡片可变字段的完整快照，不是语义不明确的局部补丁。
4. 列表删除、停止后不应继续显示或无权访问的实例放入 `removedIds`。
5. 金额字段沿用项目当前的字符串精度协议，避免 JavaScript 浮点误差。
6. 卡片名称、彩种和玩法等稳定字段继续来自首次 REST 结果；若这些字段允许编辑，则对应操作响应直接更新，随后由 REST 对账兜底。

## 9. 前端同步状态机

### 9.1 首次加载

1. 页面通过 REST 加载当前分页或当前筛选结果。
2. 建立 WebSocket。
3. WebSocket 成功订阅后执行一次 REST 对账，消除“REST 返回到订阅完成”窗口内的变化。
4. 对账期间收到的快照先缓存；REST 完成后按 `updatedAt` 再应用缓存。

### 9.2 在线状态

- 快照只更新当前已加载 ID，保持当前排序、搜索结果和分页不变。
- 本地每秒更新倒计时展示，但倒计时归零不调用 REST。
- 不运行 15 秒、60 秒或其他周期性 `/schemes/running`、`/stats` 轮询。
- 用户主动开启、停止或修改方案时，先用接口响应更新当前页面，再由实时快照校正。

### 9.3 断线和重连

1. WebSocket 断开后进入离线状态，不启动高频轮询。
2. WebSocket 自动重连并完成订阅。
3. 每个成功重连周期只执行一次 REST 对账。
4. 对账期间继续缓存新快照，对账结束后按版本合并。
5. 多个重连事件共享同一个进行中的对账 Promise，禁止并发重复请求。

## 10. 云端统计同步

取消方案卡片轮询后，不能继续依赖卡片倒计时刷新顶部统计。

统计采用独立的会员级合并器：

- 方案状态、投注流水或盈亏变化时标记会员统计为脏。
- 约 1 秒内相同会员只计算一次。
- 一次查询批量处理多个会员，通过 `GROUP BY member_id` 获取统计结果。
- 按会员发布完整统计快照。
- 前端收到后直接更新页面顶部统计。

这样不会把 `/schemes/running` 的压力转移到 `/stats`。

## 11. 最终一致性与补偿

### 11.1 NATS 连接异常

- Worker 发布失败只记录错误和待补偿标记，不影响下注主流程。
- API 节点与 NATS 断开时，主动关闭该节点浏览器 WebSocket。
- 浏览器重连到健康节点后执行一次 REST 对账。

### 11.2 慢浏览器连接

当前连接发送缓冲区满时不能继续静默丢弃消息。新设计中应关闭该慢连接，让客户端重连并执行 REST 对账。

### 11.3 数据库补偿扫描器

增加一个全局补偿扫描器：

- 约每 5 秒按 `(updated_at, id)` 游标扫描最近变化的实例。
- 使用 PostgreSQL advisory lock 保证集群中同一时刻只有一个扫描器工作。
- 按固定批次读取并发布当前快照。
- 游标和查询必须使用合适索引，禁止周期性全表扫描。
- 重复快照由 `updatedAt` 幂等处理。
- 扫描落后时连续处理有限批次后主动让出执行，避免长期占用资源。

补偿扫描的成本按全平台真实变化量增长，而不是按在线用户数量增长。

## 12. 配置

建议增加：

```env
CLOUD_REALTIME_ENABLED=true
CLOUD_REALTIME_BUS=nats
NATS_URL=nats://127.0.0.1:4222
NATS_SUBJECT_PREFIX=caipiao
CLOUD_REALTIME_COALESCE_MS=200
CLOUD_STATS_COALESCE_MS=1000
CLOUD_RECONCILE_INTERVAL_SEC=5
```

NATS 用户名、密码、Token 或凭证文件通过独立环境变量配置，不提交到代码仓库。

消息总线内部接口至少应提供：

- 发布会员范围事件；
- 订阅会员范围事件；
- 取消订阅；
- 连接状态回调；
- 健康和诊断快照；
- 关闭与资源释放。

本地开发可以保留 `local` 实现，但生产集群必须使用 `nats`。

## 13. 监控与诊断

管理员诊断接口至少展示：

- NATS 当前连接状态、断线时间和重连次数；
- 当前订阅会员数和浏览器 WebSocket 连接数；
- 合并器队列长度、脏实例数、进入事件数和合并后发布数；
- NATS 发布成功数、失败数、延迟和最后错误；
- WS 推送成功数及慢连接断开数；
- 补偿扫描游标、扫描延迟、批次数和待补偿数量；
- 客户端重连次数和重连后 REST 对账次数；
- `/schemes/running` 与 `/stats` 请求量。

结构化日志包含：

- `member_id`
- `instance_id`
- API 节点标识
- Worker 节点标识
- 消息版本
- `updated_at`
- NATS subject
- 发布或投递结果

日志不得记录第三方投注凭证、用户密码或访问 Token。

## 14. 兼容上线

采用分阶段发布：

1. 部署 NATS 和新后端；新后端发送完整快照，同时保留旧 `refresh_running_list` 提示。
2. 部署新前端；新前端消费快照，收到旧格式事件时只执行防抖后的单次 REST 对账。
3. 确认前端覆盖后关闭在线周期轮询。
4. 观察稳定后删除旧提示和旧轮询兼容逻辑。
5. 保留实时同步功能开关，异常时允许暂时恢复低频轮询，但不得影响 Worker。

升级期间，旧客户端可以继续按旧提示刷新；新客户端不会因旧后端缺少快照而完全失去更新能力。

## 15. 测试设计

### 15.1 后端单元测试

- 200ms 内相同实例多次变化只发布最后快照。
- 多实例变化只触发批量查询并按会员分组。
- 不同会员之间没有消息泄漏。
- API 动态订阅引用计数正确。
- NATS 断线不阻塞方案执行。
- WS 缓冲区满时关闭连接。
- 补偿扫描器只有一个节点取得 advisory lock。
- 重复扫描和重复发布安全。
- 统计合并器按会员合并并批量查询。

### 15.2 前端单元测试

- WS 在线时没有周期性 `/schemes/running` 和 `/stats` 请求。
- 首次连接和每次重连各执行一次对账。
- 并发重连事件不能产生重复对账请求。
- 对账期间收到的快照不会丢失。
- 旧版本快照不能覆盖新版本状态。
- 快照不改变卡片顺序、分页和搜索结果。
- 倒计时归零不触发 REST。
- `removedIds` 能删除对应卡片。

### 15.3 集成测试

- 两个 Worker 和两个 API 节点连接同一 NATS 集群。
- 用户连接任意 API 节点都能收到自己方案的变化。
- 一个会员不能收到另一会员数据。
- 重启 NATS、API 或 Worker 后系统可以恢复。
- NATS 不可用时下注与数据库状态更新继续执行。
- 断线期间发生的状态变化能被 REST 对账或扫描器修复。

### 15.4 压力测试

- 模拟大量用户和方案同时更新。
- 观察合并前后消息比率、数据库批量查询次数、NATS 延迟和 WS 队列。
- 验证慢连接不会拖慢其他用户。
- 验证补偿扫描不会造成全表扫描、长事务或数据库连接池耗尽。

## 16. 验收标准

1. WebSocket 稳定在线时，`/schemes/running` 和 `/stats` 的后台定时请求为零。
2. 每次成功重连最多执行一次 REST 对账。
3. 方案变化到卡片更新的 P95 延迟低于 1 秒。
4. 200ms 内同一实例的频繁变化最多产生一次快照发布。
5. NATS 或单个 WebSocket 异常不暂停任何方案的计算、下注或结算。
6. 集群节点切换后，最终状态能通过重连对账或补偿扫描恢复。
7. 不出现跨会员数据推送。
8. 查询数量与真实状态变化量相关，不再与在线用户数和倒计时频率线性增长。

## 17. 实施边界

实施时优先完成以下闭环：

1. 消息总线抽象和 NATS Core 实现；
2. 方案快照批量查询、合并发布和会员主题路由；
3. API 动态订阅和 WebSocket 快照转发；
4. 前端快照合并、断线对账和停止轮询；
5. 统计快照同步；
6. 数据库补偿扫描和索引；
7. 诊断、监控、集成测试及分阶段兼容清理。

任何实时同步失败都必须降级为“界面可能暂时陈旧、重连后修复”，不能升级为“方案 Worker 被阻塞”。
