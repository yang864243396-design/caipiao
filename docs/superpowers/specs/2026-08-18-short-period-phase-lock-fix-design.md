# 短周期下单相位锁修复设计

## 背景

波场 3 秒彩实例 `inst-1-1786600039439` 在后端重启后保持 `running / cloud_active`，但不再产生投注记录。现场诊断确认：periods 快照、WS 开奖、上一期开奖结果和投注窗口均正常，实例没有 pending 注单或并发排队阻塞。

worker 固定每秒执行一次；当 WS 开奖和 periods 快照在本周期稍晚到达时，真正准备下单只剩约 1.5 秒。现有逻辑在剩余时间少于 2.4 秒时额外执行最长 900ms 的会员级同步期号确认，并要求确认后仍剩 1.5 秒。对 3 秒周期而言，这组条件会稳定地拒绝每一期，形成无报错、无记录、持续运行的相位锁。

## 目标

- 短周期彩种在 periods 与 WS 两个共享快照都新鲜、都指向同一目标期且安全窗口充足时，可以直接进入第三方 Place 请求。
- 保留最终期号一致性检查和 1.2 秒封盘安全线，禁止跨期下注。
- 任一共享快照缺失、过期、目标期不一致或安全窗口不足时，继续拒绝本期下注。
- 普通周期彩种继续沿用现有近封盘同步期号确认，不改变其安全策略。
- 不增加按方案轮询，不增加数据库迁移，不改变第三方接单期不一致时的暂停规则。

## 方案比较

### 方案 A：短周期双快照一致时跳过同步确认（采用）

当 periods 快照新鲜且目标期一致，并且 WS 观察到的下一期与目标期一致、WS 快照新鲜、剩余时间大于现有 1.2 秒安全线时，`guajiPrePlaceVerificationNeeded` 返回 false。Place 前仍再次执行 periods 与 WS 的最终安全校验。

优点是没有新增网络请求和调度器，直接消除 900ms 同步确认对 3 秒窗口的挤占；两个独立共享来源仍共同约束目标期。改动范围仅限现有期号预检决策。

### 方案 B：缩短同步确认超时

把 900ms 改为更短超时。该方案仍受网络抖动和 worker 相位影响，不能消除稳定漏期，并会产生更多超时请求，因此不采用。

### 方案 C：提高 worker tick 频率

提高全局 tick 频率只能降低概率，会增加所有实例和数据库负载，且无法保证 periods 快照何时完成，不采用。

## 详细设计

在 `worker_guaji_period_verify.go` 增加一个纯判定函数，用于判断短周期的共享快照是否足以替代会员级同步确认：

1. 从 WS `PeriodState` 和 periods `PeriodsSchedule` 识别实际周期；只有周期大于 0 且不超过 15 秒才进入该分支。
2. periods 快照必须通过现有 `guajiBetSnapshotFreshAt`，且 `CurrentPeriod` 等于目标期。
3. WS 快照必须存在且新鲜，`NextIssue` 等于目标期。
4. periods 与 WS 各自计算的封盘剩余时间都必须大于 `guajiPlaceCloseSafety`（1.2 秒）。
5. 满足以上条件时不执行会员级同步期号确认；随后 `placeGuajiSchemeBet` 中既有的 `guajiBetPeriodMatches`、`guajiBetPeriodHasSafeWindowAt` 和 `guajiShortPeriodWSWindowAllowsAt` 仍在出站前执行。

普通周期、快照缺失、快照过期、错期和临近封盘继续走现有同步确认或安全跳过路径。

## 错误处理与性能

- 本修复不放宽最终 1.2 秒安全线；窗口不足仍返回 `ErrPeriodClosed`，释放尚未出站的占位。
- 不增加 HTTP 请求；正常 3 秒彩反而移除一次不必要的会员级同步确认。
- 判定只读取进程内共享快照，没有数据库写入和锁竞争，不随用户或方案数量放大外部并发。
- 第三方实际接单期与目标期不同仍记录实际期并暂停实例，不伪装成功。

## 测试

- 回归测试：3 秒周期、periods 与 WS 同期、新鲜、剩余 1.8 秒时，不需要同步确认。旧实现应失败。
- 安全测试：WS 目标期不一致时仍需要同步确认。
- 安全测试：WS 剩余时间不超过 1.2 秒时仍需要同步确认。
- 兼容测试：普通周期临近封盘仍需要同步确认。
- 运行 schemes 目标测试、相关包测试、后端全量测试和 server 构建。

## 发布验证

部署并重启后端后，观察实例 `inst-1-1786600039439`：新记录必须满足 `period_no = third_party_period`；若窗口不足可以漏掉该期，但不得连续处于所有本地前提正常却永不尝试下单的状态。
